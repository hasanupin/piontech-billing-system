Masalah yang Dipecahkan Sistem Ini

  • Rekap transaksi manual — tidak tersistem, rawan salah
  • Setiap pelanggan tanggal tagihan berbeda — sulit dipantau
  • Manajemen wilayah petugas dilakukan manual
  • Setoran petugas ke admin sering parsial, tidak tercatat rapi
  • Laporan rapat bulanan sulit disusun karena data tersebar di banyak sheet Excel

Data Eksisting — Struktur Excel Klien (Sumber Analisis)

Setiap sheet = 1 petugas per bulan, terdiri dari header (BULAN, TITIP 1-4, KEKURANGAN SETOR, KOMISI) dan tabel pelanggan (nama, Paket, Alamat, MAPS, PHOTO RUMAH, WA, KET., BAYAR). Ditemukan masalah teknis: nomor WA tersimpan scientific notation (6.28226E+12), kolom Paket hanya angka tanpa label jelas, alamat hanya nama kampung, tidak ada timestamp pada setoran.

2.1 Klarifikasi — Master Paket
Keputusan Final: Angka di kolom Paket (110, 100, 115) adalah harga dalam ribuan (Rp 110.000, dst.). Namun nama paket hanya LABEL REFERENSI untuk admin — harga bisa diinput manual per transaksi, TIDAK harus definitif mengikuti master paket.

Implikasi teknis: package_id di tabel pelanggan bersifat NULLABLE (referensi saja). Kolom billed_amount di transaksi diisi manual oleh admin/petugas — pre-fill dari default_price paket tapi tetap EDITABLE, bukan readonly/auto-lock.

2.2 Klarifikasi — Cluster Petugas
Keputusan Final: Alamat (PADI, TALANG, KEDOK, dll.) hanya menjadi REFERENSI untuk mempermudah pencarian lokasi. Acuan resmi penugasan pelanggan ke petugas menggunakan konsep CLUSTER — bukan alamat/wilayah geografis.

Implikasi teknis: Tabel baru clusters dibuat sebagai acuan utama. Satu cluster = satu petugas PIC (officer_id). Pelanggan ter-assign via cluster_id, bukan langsung ke petugas. Jika petugas ganti, admin cukup update officer_id di tabel cluster — semua pelanggan dalam cluster tersebut otomatis ikut berpindah tanpa perlu update satu-satu.

2.3 Klarifikasi — Status ISOLIR
Keputusan Final: ISOLIR BUKAN status berhenti berlangganan. ISOLIR = pelanggan sudah menerima tagihan dan MELEWATI jatuh tempo tanpa membayar, sehingga sambungan internetnya sementara diblokir. Status ini di-UPDATE MANUAL oleh admin (bukan otomatis oleh sistem).

Alur status:

AKTIF → (jatuh tempo terlewat, belum bayar) → admin klik "Tandai ISOLIR" → ISOLIR → (pelanggan akhirnya bayar) → admin klik "Pulihkan ke Aktif" → kembali AKTIF

OFF adalah status TERPISAH — hanya untuk pelanggan yang benar-benar berhenti berlangganan permanen, TIDAK ditagih lagi.

Aturan penting: Pelanggan berstatus ISOLIR TETAP muncul di daftar tagihan bulan berjalan dan HARUS tetap dibayar. Bedanya dengan OFF: OFF tidak muncul di tagihan sama sekali.

2.4 Klarifikasi — Tanggal Tagihan Berbeda per Pelanggan
Keputusan Final: Setiap pelanggan punya tanggal tagihan sendiri-sendiri (misal pelanggan A tanggal 5, pelanggan B tanggal 15), namun semua masih dalam SATU periode bulan yang sama.

Inilah alasan mengapa mekanisme titip/setoran parsial ada: karena petugas menagih bertahap sepanjang bulan sesuai jatuh tempo masing-masing pelanggan, uang yang terkumpul di tangan petugas juga masuk bertahap — bukan sekaligus di akhir bulan.

Contoh: Tgl 5 petugas menagih 10 pelanggan → dapat Rp 1.100.000 → titip ke admin Rp 1.000.000 (sisa Rp 100rb di tangan). Tgl 10, menagih 8 pelanggan lagi → dapat Rp 880.000 → titip lagi Rp 500.000. Dan seterusnya sepanjang bulan.

2.5 Klarifikasi — Alur Uang 3-State (PALING KRITIS)
Ini adalah klarifikasi paling signifikan yang mengubah desain sistem. Uang dari pelanggan punya TIGA kemungkinan state yang harus dipantau terpisah:
StateKondisiCara Sistem Mencatat
1. Tunai di PetugasPetugas berhasil menagih, uang tunai ada di tangan petugas, BELUM ada setoran sama sekali ke admin bulan iniTransaksi dicatat LUNAS oleh petugas (payment_method=cash). Setoran belum ada → ini "uang beredar di petugas"
2. Disetor Sebagian (Titip)Petugas sudah menyetor sebagian ke admin. Sisa masih di tangan petugasDicatat di tabel officer_deposits. Sistem hitung: total tagih tunai − total disetor = sisa di petugas
3. Transfer LangsungPelanggan bayar via transfer bank LANGSUNG ke rekening Pion Tech — petugas TIDAK PERLU mendatangi pelanggan ini sama sekaliAdmin catat transaksi dengan payment_method=transfer. officer_id = NULL. TIDAK masuk hitungan uang di petugas — otomatis dianggap settled
Formula kunci yang harus konsisten di seluruh sistem (dashboard, laporan, widget):
Uang di Petugas = Total Tunai Terkumpul − Total Sudah Disetor
Transfer TIDAK PERNAH masuk ke sisi manapun formula ini — dia berdiri sendiri sebagai "sudah settled langsung".
3. Alur Bisnis Lengkap

3.1 Alur Penagihan Bulanan (Step by Step)

StepAktorAktivitas
1AdminAwal bulan: sistem tampilkan daftar pelanggan per tanggal tagihan. Admin pastikan cluster & petugas sudah benar.
2PetugasSetiap hari, cek pelanggan cluster sendiri yang jatuh tempo hari itu (atau sudah lewat). Datangi & tagih.
3APetugasBayar TUNAI → petugas input transaksi. Uang ada di petugas.
3BAdminBayar TRANSFER langsung → admin input dengan payment_method=transfer. Settled langsung, tidak lewat petugas.
4AdminPelanggan lewat jatuh tempo belum bayar → admin update manual status ke ISOLIR.
5PetugasKapan saja sepanjang bulan: setor sebagian uang ke admin (titip). Admin konfirmasi & catat.
6CEO/AdminDashboard menampilkan real-time: tagihan terkumpul, sudah disetor, sisa di petugas, % pembayaran.
7AdminAkhir bulan: rekonsiliasi — total tagih = total setor + sisa yang diakui petugas.

Total Terkumpul TunaiSUM(paid_amount) WHERE payment_method=cash

Total Terkumpul SemuaTunai + Transfer

Uang di PetugasTotal Terkumpul Tunai − Total Disetor ke Admin (transfer TIDAK masuk)
